Chapter 1

Where We Are
Today

Opportunities to strengthen trigger enforcement.

Trigger Event Data Bypasses Validation

Works today

Workflow-level inputs are validated at runtime.

inputs:
  - name: message
    type: string
    required: true

Opportunity

Trigger event data (event.alerts, event.case) is not validated on manual calls.

triggers:
  - type: alert
    with:
      rule_name: "OOM in Payment API"
# No inputs — accepts anything via API
POST /run → { inputs: anything } → No trigger check → executes

Production Workflows Need Stronger Guardrails

name: Restart Payment API on OOM
triggers:
  - type: alert
    with:
      rule_name: "OOM in Payment API"

consts:
  k8s_deployment: payment-api

steps:
  - name: restart_service
    type: http
    with:
      url: "https://k8s-api.internal/..."
      method: PATCH
      # ... restarts the deployment

What can happen

  • Trigger filter is not enforced
  • Accepts empty { inputs: {} }
  • Restarts production unconditionally
  • Posts blank Slack notification

Agent scenario

AI agent misreads "check health" as "restart." Sends empty inputs. Production restarts during peak traffic.

Trigger declaration should be the guardrail — authors shouldn't need defensive if conditions in every step.

Agent Integration Needs Typed Contracts

As Agent Builder grows, agents select workflows as tools. Today, the tool contract is:

# What agents see today
tool_input: Record<string, any>
# No schema. No guidance. No validation.

The agent has no way to know this workflow expects alert data — not arbitrary inputs.

The opportunity

  • Expose trigger schemas as tool contracts
  • Agents discover required fields automatically
  • Validate data before execution starts
  • Only relevant workflows appear as tools

Every workflow with a typed manual trigger becomes a safe, discoverable agent tool.

GitHub Actions and n8n Enforce Trigger Contracts

GitHub Actions
"To enable a workflow to be triggered manually, you need to configure the workflow_dispatch event."
on:
  workflow_dispatch:
    inputs:
      logLevel:
        description: 'Log level'
        required: true
        type: choice
        options: [info, warning, debug]
n8n
"Workflows always need a trigger, or start point."
  • Requires Manual Trigger node
  • Offers Form Trigger with typed fields
  • Separates production vs manual runs
Model No trigger = no invocation, period.

Six Patterns We Can Adopt

  • Triggers are contracts — enforced at runtime, not decorative
  • Invoke a trigger, not a workflow — callers interact with typed entry points
  • Manual invocation needs a mechanism — explicit opt-in or trigger-aware form
  • Consistent event path — all triggers produce events the same way
  • Triggers gate visibility — workflows surface where triggers match
  • Trigger type determines shape — system derives forms and autocomplete

These are not product-specific choices — they are industry consensus across GitHub Actions, n8n, Datadog, and Tines. We can adopt them incrementally.

New Mental Model: Call a Trigger, Not a Workflow

Callers specify which trigger to invoke and provide data matching its schema. All data lands in event.

Today

Any caller → { inputs: anything } → No validation → executes

Proposed

Invoke trigger → Validate against schema → Inject into event → execute
No matching trigger → Rejected (400)

Hybrid Production/Test Gate

ScenarioAllowed?Context
Production + manual triggerYes — validatedisTestRun: false
Production + alert/scheduled/customSystem channels onlyN/A
Test + any triggerYes — user selects triggerisTestRun: true

Production runs (hard gate)

  • Only manual trigger invocable
  • Prevents accidental production calls
  • Agents need explicit manual trigger

Test runs (soft gate)

  • Any trigger invocable as test run
  • Execution flagged isTestRun: true
  • Existing test/prod branching works

Editor UX for Test Runs

"Test" button (top-level)

  • Opens trigger selector modal
  • Renders input form from trigger schema
  • Submitting creates isTestRun: true

Per-trigger "play" button

  • Play icon next to each trigger in YAML
  • Skips trigger selection step
  • Like existing per-step run feature

API behavior

# Production run (manual trigger only)
POST /api/workflows/{id}/run
{ "trigger": "manual",
  "event": { "alert_id": "abc" } }

# Test run (any trigger)
POST /api/workflows/{id}/test
{ "trigger": "alert",
  "event": { "alerts": [...] } }

Both validate against the specified trigger's schema before execution.

All Triggers Produce Events Consistently

All invocations — automatic or manual — produce event in the execution context. No normalization boilerplate needed.

name: Block malicious IP
triggers:
  - type: alert
  - type: manual
    event:
      $ref: alert

steps:
  # Works for both triggers
  - name: block_ip
    type: http
    with:
      url: "https://firewall.internal/..."
      body:
        source: "{{ event.alerts[0].ip }}"
        comment: "{{ event.rule.name }}"

How data flows

  • Alert fires: system injects into event
  • Manual call: caller data validated, injected into event
  • Test run: same flow, flagged isTestRun

Steps reference event.alerts regardless of source. execution.triggeredBy distinguishes the channel.

$ref: alert on the manual trigger inherits the alert event schema — no need to rewrite it.

New triggers.* Namespace in Execution Context

triggers:
  - type: alert
    with:
      rule_name: "OOM in Payment API"
  - type: manual
    event:
      $ref: alert

steps:
  - name: log
    if: ${{ triggers.alert }}
    type: console
    with:
      message: |
        Rule: {{ triggers.alert.event.rule.name }}
        Config: {{ triggers.alert.with.rule_name }}

How it works

  • triggers.alert — truthy when alert fired
  • triggers.alert.event.* — runtime data
  • triggers.alert.with.* — static YAML config
  • triggers.manual — null if not active

Editor autocomplete

  • triggers.alert.event. → alerts, rule, params
  • triggers.alert.with. → rule_name, rule_id
  • Shape resolved statically from YAML

Referenceable Schemas for Manual Triggers

Reference a predefined schema

triggers:
  - type: manual
    event:
      $ref: alert  # inherits AlertEventPropsSchema

Extend with extra fields

triggers:
  - type: manual
    event:
      allOf:
        - $ref: alert
        - properties:
            priority:
              type: string
              enum: [low, medium, high, critical]
          required: [priority]

Available references

ReferenceProvides
alertevent.alerts, event.rule
caseevent.case, event.user
Custom trigger IDRegistered eventSchema

Future: schema registry

User-defined schemas referenced via $ref: my-team/enriched-alert. Already requested by the community. The $ref pattern is forward-compatible.
