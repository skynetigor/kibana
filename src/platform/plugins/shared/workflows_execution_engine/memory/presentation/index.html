Workflow Trigger
Semantics

Why triggers must be enforced contracts, and two paths to get there.

Ihor Panasiuk · One Workflow Team · March 2025

Chapter 1

The Current
Problem

Triggers are decorative. Any workflow can be called from anywhere with any data.

Root Cause

What works

If a workflow defines an inputs section, the runtime validates them.

inputs:
  - name: message
    type: string
    required: true

Caller must provide inputs.message or the call is rejected.

What doesn't work

If a workflow relies on trigger event data (event.alerts, event.case), there is zero validation on manual calls.

triggers:
  - type: alert
    with:
      rule_name: "OOM in Payment API"
# No inputs section — API accepts anything

Caller sends { inputs: {} } — workflow runs with empty event data.

The gap

POST /api/workflows/{id}/run → { inputs: Record<string, any> } → No trigger validation. No event schema. Execution starts.

Example: Production Service Restart

name: Restart Payment API on OOM
enabled: true
triggers:
  - type: alert
    with:
      rule_name: "OOM in Payment API"

consts:
  k8s_namespace: production
  k8s_deployment: payment-api-deployment

steps:
  - name: restart_service
    type: http
    with:
      url: "https://k8s-api.internal/...
            /{{ consts.k8s_deployment }}"
      method: PATCH
      body:
        spec:
          template:
            metadata:
              annotations:
                restart-trigger: "{{ now }}"

  - name: notify_team
    type: slack
    connector-id: payments-team
    with:
      message: |
        ⚠️ *Payment API Restarted*
        Reason: {{ event.rule.name }}

What goes wrong

  • Trigger's rule_name filter is decorative — never enforced
  • No inputs section — API accepts { inputs: {} }
  • restart_service executes immediately — production restarts for no reason
  • notify_team posts to Slack with blank alert fields

🤖 Agent scenario

An AI agent misinterprets "check payment service health" and calls this workflow. It sends { inputs: {} }. The production Payment API restarts during peak traffic. No alert, no OOM — just an LLM making a bad call, and the system doing nothing to stop it.

The fix isn't to forbid manual invocation. It's to require the caller to provide data matching the alert trigger shape. Today the API accepts anything.

Chapter 2

Industry
Analysis

How GitHub Actions, n8n, Datadog, and Tines handle trigger enforcement.

Hard Gate Model

GitHub Actions
"To enable a workflow to be triggered manually, you need to configure the workflow_dispatch event."
  • No workflow_dispatch = no "Run" button, no API, no CLI
  • Defines typed inputs with description, required, default, type
  • UI renders form; API validates before execution
on:
  workflow_dispatch:
    inputs:
      logLevel:
        description: 'Log level'
        required: true
        type: choice
        options: [info, warning, debug]
n8n
"Workflows always need a trigger, or start point."
  • Manual Trigger node required for manual execution
  • Only one Manual Trigger per workflow
  • Form Trigger = manual trigger with structured input schema
  • Manual executions don't count toward billing
Model

No trigger = no invocation, period.

Soft Gate Model

Datadog Closest competitor

Layer 1: Any workflow runnable from its page — trigger-aware

"From the workflow page, click Run. Enter the values for existing trigger variables."

Layer 2: Triggers gate contextual visibility

ContextGate
Monitor notificationNeeds Monitor trigger
Security panelNeeds Security trigger
Dashboard widgetNeeds Dashboard trigger
Via APINeeds API trigger
Workflow page "Run"Always available
Tines

Action-based architecture: entry action defines the channel.

  • Webhook Action = primary entry point
  • match_rules validate incoming data shape
  • access_control: Public, Secret, Team, Tenant
  • No "any story triggerable by anything"
Model

Entry action defines invocation channel + data contract.

Chapter 3

Solution A:
Hard Gate

No trigger declaration = no invocation of that type. GitHub Actions / n8n model.

Mental Model: Call a Trigger, Not a Workflow

Every trigger is an enforced contract. The caller specifies which trigger to invoke and provides data matching its schema. All data lands in event.

Current

Any caller → { inputs: Record<string, any> } → No validation → execution starts

Proposed

Invoke manual trigger → Validate against schema → Inject into event → execute
No manual trigger → REJECTED (400)
Alert connector → System provides alert data → event.alerts, event.rule
Test run → Always allowed (isTestRun: true)

Predefined Shapes + Example

Predefined event shapes

Instead of writing full JSON Schema, reference a known shape:

triggers:
  - type: alert
  - type: manual
    event:
      shape: alert  # same as alert trigger
ShapeProvides in event
alertevent.alerts, event.rule, event.params
caseevent.case, event.user
Custom trigger IDTrigger's registered eventSchema

Custom JSON Schema also supported:

triggers:
  - type: manual
    event:
      properties:
        alert_id: { type: string }
        priority: { type: string,
          enum: [low, medium, high, critical] }
      required: [alert_id, priority]

No normalization needed

Manual trigger data lands in event — identical to a real alert. Steps work unchanged.

name: Block malicious IP
triggers:
  - type: alert
  - type: manual
    event:
      shape: alert

steps:
  # event.alerts works for both triggers
  - name: block_ip
    type: http
    with:
      url: "https://firewall.internal/..."
      method: POST
      body:
        action: block
        source: "{{ event.alerts[0].source.ip }}"
        comment: "{{ event.rule.name }}"

  - name: notify_soc
    type: slack
    connector-id: soc-alerts
    with:
      message: |
        IP: {{ event.alerts[0].source.ip }}
        Rule: {{ event.rule.name }}
        Via: {{ execution.triggeredBy }}

Agent Builder Integration

name: Enrich and escalate alert
triggers:
  - type: manual
    event:
      properties:
        alert_id:
          type: string
          description: "Alert ID to investigate"
        priority:
          type: string
          description: "Escalation priority"
          enum: [low, medium, high, critical]
      required: [alert_id, priority]

steps:
  - name: fetch_alert
    type: elasticsearch.request
    with:
      method: GET
      path: /.alerts-*/_doc/{{ event.alert_id }}

  - name: create_case
    type: kibana.request
    with:
      request:
        method: POST
        path: /api/cases
        body:
          title: "[{{ event.priority | upcase }}] ..."
          severity: "{{ event.priority }}"

What the agent sees

The manual trigger's event schema is exposed as the tool input contract.

  • alert_id — string, required
  • priority — enum [low, medium, high, critical], required

Data lands in event. No guessing.

Chapter 4

Solution B:
Soft Gate

Any trigger can be invoked manually. Datadog model.

Mental Model: Invoke Any Trigger Manually

Same principle: call a trigger, not a workflow. But any trigger is manually invocable — no separate manual trigger needed for existing trigger types.

Layer 1: Trigger-aware manual run

When clicking "Run" on any workflow page:

  • System shows list of defined triggers
  • User selects which trigger to invoke
  • System renders fields from trigger's event schema
  • Validates data → injects into event
Select alert trigger → Provide alert data → event.alerts

Layer 2: Contextual visibility gating

ContextRequired trigger
Rule actions dropdownalert
Case automationcases.*
Agent Builder toolsmanual
API invocationAny (caller specifies)
Workflow page "Run"Always available

When do you need manual trigger?

Only for custom event shapes not covered by other triggers.

What's different

  • System derives the form from the alert trigger's event schema
  • Caller provides alert-shaped data — validated before execution
  • Data injected into event — identical to a real alert
  • Steps reference event.rule.name — works for both

API call

# POST /api/workflows/{id}/run
{
  "trigger": "alert",
  "event": {
    "alerts": [...],
    "rule": { "name": "OOM in Payment API" }
  }
}

Caller specifies which trigger. System validates against that trigger's schema.

Recommendation

Either model is vastly better than the current state. Both enforce trigger contracts and validate data before execution.

The current state — zero enforcement — is not defensible for a security automation product.

Summary

Let's discuss.

Triggers should be enforced contracts — defining both the invocation channel and the data shape. The industry agrees. We need to pick a model and implement it.
