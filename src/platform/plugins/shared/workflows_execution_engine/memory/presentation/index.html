Workflow Trigger
Semantics

Why triggers must be enforced contracts, and two paths to get there.

Ihor Panasiuk · One Workflow Team · March 2025

Bottom line up front

Trigger declarations are ignored at runtime. Any workflow can be called with any data via the run API, bypassing all trigger contracts. This enables accidental service restarts, garbage case creation, and unvalidated agent calls in production.

  • Problem: Trigger event data bypasses all validation on manual calls
  • Evidence: Every competitor enforces trigger contracts; we are the only one that does not
  • Proposal: Two models available — hard gate (GitHub Actions) or soft gate (Datadog)
Chapter 1

The Current
Problem

Triggers declare intent but are never enforced at runtime.

Trigger Event Data Bypasses All Validation

Validated today

Workflow-level inputs are checked at runtime.

inputs:
  - name: message
    type: string
    required: true

Never validated

Trigger-implied event data (event.alerts, event.case) has zero validation on manual calls.

triggers:
  - type: alert
    with:
      rule_name: "OOM in Payment API"
# No inputs section — accepts anything
POST /run → { inputs: Record<string, any> } → No trigger check → execution starts

Unvalidated Call Restarts Production Service

name: Restart Payment API on OOM
enabled: true
triggers:
  - type: alert
    with:
      rule_name: "OOM in Payment API"

consts:
  k8s_namespace: production
  k8s_deployment: payment-api-deployment

steps:
  - name: restart_service
    type: http
    with:
      url: "https://k8s-api.internal/...
            /{{ consts.k8s_deployment }}"
      method: PATCH
      body:
        spec:
          template:
            metadata:
              annotations:
                restart-trigger: "{{ now }}"

  - name: notify_team
    type: slack
    connector-id: payments-team
    with:
      message: |
        *Payment API Restarted*
        Reason: {{ event.rule.name }}

What goes wrong

  • Ignores trigger rule_name filter
  • Accepts empty { inputs: {} }
  • Restarts production unconditionally
  • Posts blank Slack notification

Agent scenario

AI agent misinterprets "check service health" and calls this workflow. Sends { inputs: {} }. Production restarts during peak traffic. No alert existed.

Manual invocation is fine — but the API must require alert-shaped data, not accept anything.

How GitHub Actions, n8n, Datadog, and Tines handle trigger enforcement.

GitHub Actions and n8n Block Untyped Calls

GitHub Actions
"To enable a workflow to be triggered manually, you need to configure the workflow_dispatch event."
  • Requires workflow_dispatch to enable manual run
  • Defines typed inputs with defaults
  • Validates before execution
on:
  workflow_dispatch:
    inputs:
      logLevel:
        description: 'Log level'
        required: true
        type: choice
        options: [info, warning, debug]
n8n
"Workflows always need a trigger, or start point."
  • Requires Manual Trigger node
  • Offers Form Trigger with typed fields
  • Separates production vs manual runs
Model

No trigger = no invocation, period.

Chapter 3

Solution A:
Hard Gate

No trigger declaration = no invocation. GitHub Actions / n8n model.

Callers Invoke Triggers, Not Workflows

Every trigger defines an event contract. Callers specify which trigger to invoke and provide matching data. All data lands in event. No manual trigger = no manual invocation.

Current

Any caller → { inputs: anything } → No validation → execute

Proposed

Invoke manual trigger → Validate against schema → Inject into event → execute
No manual trigger → REJECTED (400)
Alert connector → System provides alert data → event.alerts, event.rule

Predefined Shapes Eliminate Boilerplate

Reference a known shape instead of writing JSON Schema:

triggers:
  - type: alert
  - type: manual
    event:
      shape: alert  # same contract as alert trigger
ShapeProvides in event
alertevent.alerts, event.rule
caseevent.case, event.user
Custom IDRegistered eventSchema

Custom schema also supported:

triggers:
  - type: manual
    event:
      properties:
        alert_id: { type: string }
        priority:
          type: string
          enum: [low, medium, high, critical]
      required: [alert_id, priority]

No normalization needed

Manual trigger data lands in event — steps work unchanged.

name: Block malicious IP
triggers:
  - type: alert
  - type: manual
    event:
      shape: alert

steps:
  - name: block_ip
    type: http
    with:
      url: "https://firewall.internal/..."
      method: POST
      body:
        action: block
        source: "{{ event.alerts[0].source.ip }}"
        comment: "{{ event.rule.name }}"

  - name: notify_soc
    type: slack
    connector-id: soc-alerts
    with:
      message: |
        IP: {{ event.alerts[0].source.ip }}
        Via: {{ execution.triggeredBy }}

Agents Discover Contracts Automatically

name: Enrich and escalate alert
triggers:
  - type: manual
    event:
      properties:
        alert_id:
          type: string
          description: "Alert ID to investigate"
        priority:
          type: string
          enum: [low, medium, high, critical]
      required: [alert_id, priority]

steps:
  - name: fetch_alert
    type: elasticsearch.request
    with:
      method: GET
      path: /.alerts-*/_doc/{{ event.alert_id }}

  - name: create_case
    type: kibana.request
    with:
      request:
        method: POST
        path: /api/cases
        body:
          title: "[{{ event.priority | upcase }}] ..."
          severity: "{{ event.priority }}"

What the agent sees

Event schema exposed as tool contract:

  • alert_id — string, required
  • priority — enum, required

Data lands in event. No guessing.

Chapter 4

Solution B:
Soft Gate

Any trigger becomes manually invocable. Datadog model.

Any Trigger Becomes Manually Invocable

Same principle: call a trigger, not a workflow. But any trigger can be invoked manually — no separate manual trigger needed for existing types. manual trigger exists only for custom event shapes.

Layer 1: Trigger-aware manual run

  • Select which trigger to invoke
  • Render fields from trigger's schema
  • Validate data before execution
  • Inject into event
Select alert trigger → Provide alert data → event.alerts

Layer 2: Contextual visibility

ContextRequired trigger
Rule actionsalert
Case automationcases.*
Agent Buildermanual
Workflow pageAlways available

When is manual trigger needed?

Only for custom shapes not covered by other triggers.

System Derives Input Forms From Triggers

Run: Restart Payment API on OOM

Select trigger to invoke:

Alert trigger
rule: OOM in Payment API

Provide alert event data:

OOM in Payment API
payment-api-prod-01
abc-123-def-456
Cancel
Run

What changes

  • Derive form from trigger's event schema
  • Validate alert-shaped data before execution
  • Inject into event
  • Steps work unchanged for both sources

API call

# POST /api/workflows/{id}/run
{
  "trigger": "alert",
  "event": {
    "alerts": [...],
    "rule": { "name": "OOM in Payment API" }
  }
}

Caller specifies trigger. System validates.

Recommendation

Either model is vastly better than zero enforcement. Both validate data and expose contracts to callers.

The current state is not defensible for a security automation product.
